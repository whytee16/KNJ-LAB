# SECURITY — KNJ LAB

## 1. Сообщить об уязвимости

Не создавайте публичный issue. Напишите владельцу репозитория напрямую (контакт будет указан на сайте в разделе «Безопасность»).

## 2. Персональные данные несовершеннолетних

- **Локализация**: БД, файловое хранилище, бэкапы и серверный код, обрабатывающий ПДн, — в Казахстане ([ADR-0001](docs/adr/0001-kz-data-residency.md)).
- **Согласие законного представителя**: аккаунт ученика создаёт/подтверждает родитель; согласие фиксируется в `consents` с версией документа.
- **Минимизация**: у ученика — отображаемое имя (можно псевдоним), класс, язык, логин. Не собираем: ИИН, фото, телефон, адрес, школу (опционально только тип программы).
- Родитель видит только своих детей (`parent_student_links.status = 'active'`).
- Внешним сервисам (TTS, аналитика, e-mail) не передаются данные ученика. TTS получает только тексты учебного контента; аналитика — обезличенные события.
- Публичных профилей, рейтингов с именами и рекламы внутри детского кабинета нет.
- Удаление/анонимизация по запросу родителя; сроки хранения утверждает юрист.

## 3. Аутентификация и сессии

- Supabase GoTrue: bcrypt-хэши паролей, пароли ≥ 8 символов с латинскими буквами и цифрами (одинаковое правило в GoTrue и в формах). Проверка по списку утёкших паролей — опционально, позже.
- E-mail родителя обязательно подтверждается; ученики входят по логину, их технический адрес на домене `.invalid` никогда не получает писем, пароль ученика меняет родитель.
- Ответы входа и восстановления пароля не раскрывают, существует ли аккаунт.
- Cookie сессии `HttpOnly; Secure; SameSite=Lax`; ротация refresh-токенов.
- Rate limiting входа, регистрации, восстановления пароля и действий родителя (Postgres, ключи — хэши; [ADR-0005](docs/adr/0005-rate-limiting-in-postgres.md)) плюс встроенные лимиты GoTrue.
- 2FA (TOTP) обязательна для всех сотрудников студии (`content_manager`, `reviewer`, `admin`): без подтверждённого фактора студия недоступна, а политики БД требуют `aal2` для любой записи сотрудника. Входы сотрудников и подключение фактора пишутся в `audit_logs`.
- Первый администратор назначается оператором с доступом к БД: `DATABASE_URL=… pnpm admin:grant-role email admin` (запись в аудит); дальше роли меняет администратор в студии.

## 4. Авторизация

- Три слоя: middleware → серверный `authz` → RLS. Скрытие кнопок не является защитой.
- `service_role` ключ используется только на сервере (`src/lib/supabase/admin.ts` с `server-only`, worker, webhook) после проверки прав в `src/server/authz.ts`; никогда не попадает в браузер.
- Роли выдаёт только сервер: новый аккаунт всегда `parent`, ученик — через `register_student`, остальные роли — аудируемым изменением `profiles.role`.
- Защищённые страницы проверяют сессию через `getUser()` (проверка токена сервером авторизации), а не только cookie.
- Функции `security definer` с фиксированным `search_path`.
- Каждая RLS-политика покрыта pgTAP-тестом; новая таблица без RLS блокирует CI.

## 5. API и ввод

- Zod-валидация всех входных данных; ограничение размера тела.
- Идентификаторы — UUID; доступ проверяется по владельцу, не по «знанию ID» (IDOR).
- CSRF: Server Actions Next.js (проверка Origin) + SameSite cookie.
- CSP со строгим `script-src` (nonce), `frame-ancestors 'none'`, HSTS.
- Markdown контента рендерится без «сырого» HTML и с санитизацией (rehype-sanitize) до применения KaTeX (`trust: false`); ошибки LaTeX блокируют отправку и публикацию.
- Rate limit по IP и пользователю (Postgres).
- CSP с nonce на каждый запрос (`proxy.ts`); поэтому все страницы рендерятся динамически.
- Редиректы после входа и из писем — только на пути того же языка (`safeNext`) и на origin из `APP_URL`, а не из заголовка Host.

## 6. Платежи

- Карточные данные не обрабатываются и не хранятся — только redirect/виджет провайдера.
- Доступ активируется **только** по проверенному webhook (подпись + сверка суммы и заказа), с идемпотентностью (`payment_events` UNIQUE).
- Возврат пользователя на сайт ничего не активирует.
- Reconciliation с провайдером для пропущенных уведомлений.
- Ручная выдача доступа — только admin, с причиной и записью в `audit_logs`.
- Fake-провайдер доступен только в тестах; при старте production его наличие — фатальная ошибка.

## 7. Секреты

- Никаких секретов в Git. Шаблон — [.env.example](.env.example). `gitleaks` в CI и pre-commit.
- Production-секреты — в секрет-хранилище облака/CI, ротация при уходе участника.

## 8. Журналирование и мониторинг

- `audit_logs` (append-only): смена ролей, публикация контента, тарифы, возвраты, ручная выдача доступа, удаление аккаунтов, вход администраторов.
- Логи приложения без ПДн (ID вместо имён, без payload webhook).
- Алерты: ошибки 5xx, неверные подписи webhook, расхождения сумм, неуспешные бэкапы.

## 9. Резервное копирование

- WAL-G: непрерывная архивация WAL + ежедневный full backup в S3-хранилище РК, шифрование, хранение 30 дней.
- Ежедневный автоматический restore в изолированное окружение + проверка целостности.
- RPO ≤ 15 мин, RTO ≤ 4 ч.

## 10. Зависимости

Renovate, `pnpm audit` в CI, проверка лицензий (только MIT/Apache/BSD/ISC/LGPL-динамически; GPL/коммерческие — через ADR).
